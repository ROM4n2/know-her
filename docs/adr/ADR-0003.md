# ADR-0003 · 速测题数据从「共享单文件」改为「按 slug 侧车文件 + 构建期自动发现」

- 状态：**Proposed**（待用户拍板后转 Accepted）
- 日期：2026-10-03
- 决策人：用户（主持 agent：CodeBuddy）
- 输入：三席专家群审（`code-reviewer` / `sre-resilience` / `product-ux`）+ 两名怀疑者反证产出的 P0-3 及其已知代价；`pnpm test` 中 G1/G3/G7/G9 四组门禁的既有契约
- 关联决策：`ADR-0002`（内容形态双轨制：速测题是「每日一答」形态的载体）；与 P0-3 修复（候选 PR 注入速测题占位）直接相关

---

## 1. Context（背景与动因）

### 1.1 症状：共享热点文件

`src/data/dailyQuiz.ts` 用**一个对象字面量**承载全部速测题：

```
export const DAILY_QUIZZES: Record<string, QuizItem> = {   ← 第 18 行
  'contraception-condoms': { ... },
  ...共 26 条...
};
```

P0-3 修复（2026-10-02）让**每日候选 PR 都会向这个对象的末尾追加一条占位**。于是每个候选 PR 都触碰 `src/content/articles/<slug>.mdx` **和** `src/data/dailyQuiz.ts`——后者是**所有候选共用的同一片区域**。多 PR 并存时 GitHub 必然报 `CONFLICTING`。

这与 2026-10-02 那次台账冲突**同源**：共享热点从 `scripts/.curate-ledger.json` 转移到了题库。当时的判断是「两害取轻」——不注入则 G1 必红，代价更大——并明确记录「根治需拆 `src/data/quizzes/<slug>.ts` 侧车文件，**应单开 ADR**」。本 ADR 即那份记录。

### 1.2 更深的问题：门禁与注入器都在**解析 TS 文本**

现状两条关键路径都依赖对 `dailyQuiz.ts` 的**文本正则**：

| 位置 | 手法 |
|---|---|
| `test_daily_loop.py:quiz_keys()`（约 302-313 行） | 剥注释后正则 `^\s*'([a-z0-9][a-z0-9-]*)'\s*:\s*\{` 提取 slug 键 |
| `test_daily_loop.py:count_quiz_pool()`（约 271-281 行） | 同上正则计数 |
| `curate_harvester.py:_find_object_close()` | 字符串感知的花括号深度匹配，定位对象末尾插入点 |

这意味着：**一次 prettier 重排、一次引号风格调整、或对象被拆成多段**，都可能让 G1 门禁静默漏判——而 G1 是「文章 ↔ 速测题 1:1」的唯一执行者。项目此前已在 `rotation.ts` 上因同类问题吃过亏（轮换数学被抄两份，现已收敛为单一真值源）。

### 1.3 现状约束（不可破坏的既有契约）

- `src/pages/index.astro:9` 以 `from '../data/dailyQuiz'` 导入 `DAILY_QUIZZES` 与 `getTodayIndex`；该导入路径**不得破坏**。
- `test_daily_loop.py:validate_daily_quiz_reexport()` 要求 `dailyQuiz.ts` 必须 `from './rotation'` 转出轮换数学。
- G3 的 `lcm(文章池, 词条池)` 天数推导依赖 `count_quiz_pool()` 的口径，**必须与 G1 的 slug 集合口径完全一致**。
- G7 / G9 断言 `inject_quiz_placeholder` 的幂等性与三态可区分结果。

---

## 2. Decision Drivers（决策驱动）

1. **写路径必须只碰自己新增的文件**——候选 PR 的冲突概率趋近于零，而不是「靠指引让维护者手工解冲突」。
2. **门禁与注入器改用结构化事实**（文件名 / 目录存在性），不再解析 TS 文本。
3. **既有导入路径与门禁口径零破坏**（1.3 全部条目）。
4. **零新增依赖**：`import.meta.glob` 是 Vite / Astro 内建能力。
5. **迁移可一次性完成**，且 G1 的 1:1 在迁移全程任何一步都不得变红。
6. slug ⇄ 题 的对应关系应当**由文件系统结构保证**，而不是由对象键的书写位置保证。

---

## 3. Decision Outcome（核心决策）

### D12. 速测题改为「按 slug 侧车文件 + 构建期 glob 自动发现」，`dailyQuiz.ts` 退化为薄壳

**结构**

```
src/data/quizzes/
  contraception-condoms.ts        ← export const quiz: QuizItem = { ... }
  contraception-oral-contraceptives.ts
  ...（每个文章 slug 一个文件）
src/data/dailyQuiz.ts             ← 薄壳：QuizItem 类型 + glob 组装 + rotation 转出
```

**具体约定**

1. 每个侧车文件导出**一个**题目对象，文件名（去扩展名）**就是** slug，构成唯一键。
2. `src/data/dailyQuiz.ts` 保留：
   - `QuizItem` 类型定义（单一真值源）；
   - `export { getDayOfYear, getTodayIndex } from './rotation';`（**原样保留**，不破坏既有契约）；
   - 由 `import.meta.glob` 组装并继续导出 `DAILY_QUIZZES`，**保持 `from '../data/dailyQuiz'` 的既有导入路径不变**（`index.astro` 零改动）。
3. **G1 门禁改读目录**：`quiz_keys()` / `count_quiz_pool()` 改为列举 `src/data/quizzes/*.ts` 的文件名，**删除全部 TS 文本正则**。G1 与 G3 因此共享同一口径来源（目录），不可能再各自漂移。
4. **`inject_quiz_placeholder` 改为「创建侧车文件」**：文件已存在 ⇒ 幂等跳过（`already_present`）；写入失败 ⇒ `failed:<原因>` 并非零退出（沿用 P1-2 建立的三态可区分契约）。幂等性由「键存在性」升级为「文件存在性」，**失败态天然可区分**。
5. **候选 PR 的改动面收敛为两个新文件**：`<slug>.mdx` + `quizzes/<slug>.ts`，二者都是**新增**，互不重叠 ⇒ 无共享热点。
6. 撤销 PR 正文里「`dailyQuiz.ts` 冲突时保留双方条目」的化解指引（不再存在该冲突面），改为「编辑 `src/data/quizzes/<slug>.ts` 补全题目」。

## 4. Alternatives Considered（备选与否决理由）

| 方案 | 内容 | 裁决 |
|---|---|---|
| **A. 保持单文件 + 确定性插入锚点** | 注入点按 slug 字典序定位，使两分支的 hunk 尽量不重叠，git 可自动合并 | **否决**。仍是同一文件；两个新 slug 的字典序位置很可能相邻 ⇒ 仍冲突；文本正则门禁的脆弱性**完全保留**。只把冲突概率从「必然」降到「常见」。 |
| **C. 并入 articles content collection** | 每篇文章目录旁放 `quiz.md`，或把 `QuizItem` 塞进文章 frontmatter | **暂缓（记录为后续演进方向）**。它能给出**结构性**的 1:1 保证（题与文同生共死），是最强方案；但 `options: string[]` 放进 YAML frontmatter 可读性明显下降，且「人工补题」的占位锚点在 MDX 里不如 TS 直观。适合在速测题需要多媒体或需要「一篇多题」时再启用。 |
| **D. 接受冲突 + 自动串行化** | 同一时刻只允许存在 1 个 open 候选 PR | **否决**。把「多 PR 并行审阅」降级为单队列，牺牲维护者批量审阅的自由；且**不解决**已关闭 PR 的残留分支问题（那是 P0-1 的另一码事）。 |
| **E. 维持现状 + 靠人工解冲突** | 保留 P0-3 修复与化解指引 | **否决**。冲突每日必然发生，把结构性成本持续转嫁给维护者，且掩盖了 1.2 的文本解析脆弱性。 |
| **F. 拆成侧车文件 + 手写 barrel 索引** | 每 slug 一个文件，另建 `index.ts` 汇总 import | **否决**。barrel 本身又是一个共享热点文件（每加一条都要改它），只是把冲突从对象末尾挪到 barrel 末尾。改用 `import.meta.glob` 后**根本不需要 barrel**。 |

## 5. Consequences（影响）

### 正面

1. **冲突概率趋零**：候选 PR 只新增两个互不重叠的新文件。
2. **门禁从「解析文本」升级为「比对结构」**：G1 不再可能被格式化改动误伤；G1 与 G3 口径同源，不会再各自漂移。
3. **注入器幂等语义更强**：文件存在性判定无歧义，且「失败」不再与「已存在」混淆（正是 P1-2 的教训）。
4. **PR diff 更可读**：一篇文章对应一个题目文件，人工补题时上下文集中。
5. 与 `rotation.ts` 的「单一真值源」治理思路一致——本决策是把同一原则应用到题库。

### 负面与成本（必须如实承担）

1. **一次性迁移 26 条题目**：需迁移脚本 + 全程 G1 保持绿；迁移本身是一次有风险的重构。
2. **文件数从 1 增至 27**：目录噪声上升；`ls` 视图变长（可接受）。
3. **`import.meta.glob` 是构建期能力**：要求**字面量路径**（不可拼接），且需保证 `astro check` 的类型推断可用（侧车文件必须显式标注 `QuizItem` 类型）。
4. **门禁改动面较大**：`quiz_keys()` / `count_quiz_pool()` / G1 反向夹具 / G7 / G9 断言 / 模板与 PR 文案全部需要同步，单点遗漏会造成「门禁静默失效」。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 迁移过程中 G1 短暂变红 | 迁移必须**一个 PR 完成**，不允许「先删后加」分两步；PR 内跑 `pnpm test`（含 G1/G3/G7/G9） |
| `import.meta.glob` 类型推断失败导致 `pnpm check` 红 | 侧车文件统一 `export const quiz: QuizItem = {...}`，显式标注类型；迁移 PR 必须 `astro check` 0 errors |
| 新门禁（读目录）被「目录为空」静默通过 | 沿用既有「反空转」模式：断言必须观测到 ≥1 个侧车文件，否则记错误 |

## 6. Migration Plan（落地清单）

1. **建目录 + 迁移脚本**：新增 `src/data/quizzes/`；写一次性迁移脚本把 `DAILY_QUIZZES` 的 26 条拆成 26 个侧车文件（脚本建议留在 `scripts/` 以便复跑与审计）。
2. **薄壳改造**：`src/data/dailyQuiz.ts` 改为「`QuizItem` 类型 + `import.meta.glob` 组装 + 原样转出 `./rotation`」。
3. **门禁改造**（`scripts/test_daily_loop.py`）：
   - `quiz_keys()` / `count_quiz_pool()` 改读 `src/data/quizzes/*.ts` 文件名，删除 TS 文本正则；
   - `validate_quiz_coverage()` 的错误文案改为指向侧车文件路径；
   - 反向夹具从「1 篇文章 + 0 道题（空对象字面量）」改为「1 篇文章 + 空题目录」；
   - 新增断言：薄壳**不得**再内联对象字面量、**必须**用 glob 组装（防回退）。
4. **流水线改造**（`scripts/curate_harvester.py`）：
   - `QUIZ_FILE` → `QUIZ_DIR`（目录）；
   - `inject_quiz_placeholder()` 改为创建侧车文件，保留既有签名语义与三态可区分结果；
   - `create_draft_pr` 的 `git add` 改为新增的那个侧车文件路径；
   - 模板与 PR checklist 文案：「在 `src/data/quizzes/<slug>.ts` 中补全题目」。
5. **删除** PR 正文里「`dailyQuiz.ts` 冲突时保留双方条目」的化解指引。
6. **验收**：`pnpm check`（0 errors）+ `pnpm test`（7 套门禁全绿、36 页）+ `pnpm curate:check`（26/26）；并**变异自证**：删掉一个侧车文件 ⇒ G1 判红；恢复 glob 为内联字面量 ⇒ 新增断言判红。

---

## 7. Revisit Triggers（何时重新评估本决策）

- 速测题需要**多媒体**（图片 / 音频）或需要**一篇多题**制 ⇒ 本方案的「一 slug 一文件」不再合适，应直接跳到备选 **C**（content collection）。
- 侧车文件数量超过约 **200** 篇 ⇒ 应按四分类分目录，避免单目录膨胀。
- 若未来出现第二个「与文章 1:1 的数据」维度（如「每篇一图」「每篇一延伸阅读」），**不要**复制本方案，而应统一收敛为「随文章同源存放」，即备选 **C**。
